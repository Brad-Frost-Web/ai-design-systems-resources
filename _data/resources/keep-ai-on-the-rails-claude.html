An AI & Design Systems Online Course Lesson

Keep AI on the Rails of Your Design System

AI will hallucinate UI and make a huge mess without the proper guardrails in place. Here is a detailed breakdown of how we get AI to (faithfully! consistently! repeatedly!) build UI only using our Eddie Design System.

This is one of over 150 lessons from AI & Design Systems, an online course by me (Brad Frost), TJ Pitre, and Ian Frost. To watch the in-depth video walkthrough, get installable skills, and join a vibrant community of AI & Design Systems practitioners, join the course!

Ai Dev Concepts & Techniques
  • AI Agent User Settings

    The default user settings that the AI agent applies to every project, in every session, regardless of the project.

    In my setup I declare non-negotiables in my settings: only use the Eddie ecosystem, don't use third-party libraries, a11y++.

  • Project rule files

    Project files containing rules an agent loads at the start of every session. With multiple rule files, most-specific file wins.

    In my setup AGENTS.md → CLAUDE.md → SPEC.md, carrying the mandatory STOP & ground preamble.

  • MCP connection

    Model Context Protocol is an open standard that connects agents to other systems, data, and services.

    In my setup, the eddie-brain MCP server is what AI agents connect to in order to use the eddie_* tools.

  • Skills & reusable procedures

    Packaged workflows that auto-trigger on matching work and run specific sequences.

    In my setup eddie-web-developer fires on any UI work and brings the grounding-first sequence along.

  • Hooks & CI gates

    Automated checks, tests, and evals that run outside the agent after generations, commits, and pull requests.

    In my setup An eddie-brain validate hook runs after generations that warns, but blocks in Station 8 is The Steel Curtain.

You enter a prompt
“Build a tertiary button variant.”
"Make a product card recipe.”
“Build me a pricing page.”
1Stop & ground

Always check the live design system first

The rule files mandate that that no code can be authored until Eddie's live catalog is pulled into in the session. check_health checks Eddie components, tokens, recipes, and the reporter feedback loop.

  • check_health
  • get_component

Prevents AI from writing from memory or a stale prior session, which leads to innacurate & hallucinated UI.

2Rules

Learn rules & standards

Agents are instructed to strictly follow bfw-process configuration rules, which amongst other things declares the Eddie-Only Rule: no custom markup, no custom CSS, no hardcoded values.

  • bfw-process
  • AGENTS.md
  • CLAUDE.md

Prevents ad-hoc .my-card CSS, Google-Font links, hardcoded hex & pixels, competing UI frameworks.

3Consult

Look up real components & tokens

eddie-brain connects via MCP and provides the knowledge graph: all tokens, components, props, slots, relationships, and more.

  • search
  • get_component
  • get_token
  • get_relationships

Prevents invented props, slots (e.g. slot="eyebrow"), and incorrect compositions.

4Compose

Compose using design system ingredients

Agents are instructed to compose the UI from system-defined page templates, recipes, and components. Eddie's component graph and guidelines must be strictly followed.

  • list_pages
  • compose_recipe
  • ed-p-* templates

Prevents building from primitives — stacked card grids, missing ed-grid-item, hand-rolled chrome.

5Validate

Validate the generated code

When generation stops, a validation loop scans for token, naming, contract, and accessibility violations. Failures are returned to the agent for correction.

  • validate_file
  • suggest_fix
  • pre-commit hook

Prevents hardcoded values, broken BEM naming, placeholder link text, missing knockout on dark bands.

6Render

Render & check the output

render-check plus a live browser preview prove the markup produces real, visible output — the agent checks the displayed result, not just the code.

  • render-check
  • browser preview

Prevents silently-dropped slots and broken renders — markup that parses perfectly and displays nothing.

7Human review

You review the rendered results from step 6

You review the rendered UI, and either approve it, deny it, or request tweaks. Agent loops through Consult → Render until you approve.

  • your brain
  • your judgement

Prevents shipping on the model's say-so — taste, product intent, and "is this actually good?" stay human.

8The Steel Curtain

Run CI gates, deterministic tests & AI evals

All work goes through a pull request that must clear an array of CI tests before it can merge. Deterministic tests check accessibility, responsive, user flows, and performance. ALSO, AI evals do a two-axis review to see if it follows the repo’s standards, and actually does what the issue and FEATURE-SPEC.md actually asked for.

  • CI
  • bfw:verify:tests
  • bfw:verify:a11y
  • bfw:verify:responsive
  • bfw:verify:flows
  • bfw:verify:perf
  • two-axis eval

Prevents regressions, broken flows, accessibility issues, and off-spec work from reaching main.

9Human review

You approve to merge the work

Every gate came back green — but green is not approval. A person reads the diff, weighs it against what the ticket actually asked for, and makes the call. Merging is a decision, not a status.

  • PR review
  • your judgement
  • human approval

Prevents a green build being mistaken for a good one — no agent merges its own work.

Launch
UI Work Ships!
The work (tertiary button, product card recipe, pricing page, or whatever else was prompted) ships to production, powered entirely by the design system’s components, tokens, recipes, organizational standards, and infrastructure.
Product Design System Feedback Loop
Every product installs eddie-reporter, which scans the codebase for what Eddie infrastructure it actually uses (components, recipes, pages, tokens, charts, etc). This gets reported back to eddie-brain as learning, adoption and activity. Hacks, gaps, and problems become Eddie Design System GitHub issues, which get addressed and fed back to the product ecosystem. Hooray, quality feedback loops!
Eddie Design System

eddie-brainEddie Design System’s machine-readable knowledge graph that AI agents communicate with via MCP.

  • components.json
    Every component, recipe and page, with its real props, slots and guidelines. What the agent reads instead of guessing.
  • tokens.json
    Every design decision as a named value, across every theme. The agent asks for a token, never a hex code.
  • recipes.json
    The compositions we’ve blessed as the canonical way to build a given pattern.
  • learning.json
    What the brain suggested, and whether a human took it. The record that sharpens the next suggestion.
  • adoption.json
    Which products depend on the system, what version they’re on, and how far they’ve drifted.
  • activity.json
    What downstream products actually use, reported back from real shipped code.
Eddie DS PackagesEddie manages multiple UI packages in a monorepo and publishes via npm.
  • eddie-design-tokens
    The raw design decisions — color, space, type, motion — as named values every other package builds on.
  • eddie-web-components
    The component library itself. Framework-agnostic custom elements you can drop into anything.
  • eddie-recipes
    Larger compositions built from the core components, for patterns that repeat across products.
  • eddie-pages
    Whole page templates, so nobody starts from a blank file or assembles a layout from scratch.
  • eddie-icons
    The icon set, delivered as components so icons theme along with everything else.
  • eddie-charts
    Data visualization recipes, so charts inherit the system instead of arriving with their own look.
  • eddie-brain
    The MCP server and knowledge graph. How an agent asks the system what actually exists.
  • eddie-reporter
    Installed into products to scan for system usage and report it back upstream.
  • eddie-boilerplates
    Starter projects already wired to the system, so a new site begins on the rails.
  • eddie-website
    The (neglected!) reference site — documentation, guidelines and live examples for people.
bfw-process
Brad Frost Web’s official development standards

A versioned rulebook installed into the repo as a pinned dependency — adopted, not reinvented. It carries six phases, nine checklists, the spec templates, the Eddie-usage rules and a validation hook. .bfw-process/config.json sets the mode, the project type, the branch model (trunk or gitflow) and whether the ship gate has teeth. Two gates are human. Phase 2 won’t open Phase 3 until FEATURE-SPEC.md is approved, and Phase 5 won’t open Phase 6 until npm run bfw:ship exits zero — which only a named owner can override, and every override is written to a log.

The lesson underneath the diagram: not one of these stations trusts the model to remember the design system. Each forces a check against live, machine-readable truth — and each catches a different class of hallucination, so a miss at one station is caught at the next. The rails are installed by shared process (bfw-process) and configuration, not left to willpower, and the trust is layered — the commit hook only whispers a warning while CI is the wall that stops a bad merge.
